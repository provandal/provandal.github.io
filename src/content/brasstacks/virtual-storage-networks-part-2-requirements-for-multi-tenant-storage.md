<p>In <a href="/brasstacks/virtual-storage-networks-part-1/" target="_self">part 1</a> of this series, I introduced the concept of a Virtual Storage Network, provided some background information and stated what we believe the requirements for multi-tenant storage are.&#0160; In this post I’ll dig into the details of those requirements.</p>
<h2>Requirements for multi-tenant storage</h2>
<p>As stated before, the following requirements were gathered by speaking with several of our customers who are interested in multi-tenancy.&#0160; I’ll describe each in detail and then in the next section, describe a couple of topologies that satisfy all of these requirements.&#0160; The detailed explanations for each requirement will provide at least one specific example describing why the feature is needed.&#0160; The example may or may not be the most realistic example possible, but it will be the example that I feel makes it easiest to describe why the requirement was asked for.&#0160; Finally, keep in mind, the order does not indicate priority.</p>
<ol start="1" type="1">
<li>Namespace isolation</li>
<li>Prevent noisy neighbor problems</li>
<li>Provide Bandwidth /IOPS / response time guarantees</li>
<li>Tenant traffic identification</li>
<li>Storage Network Service Insertion (e.g., encryption)</li>
<li>Authentication (e.g., CHAP)</li>
<li>Do not rely on Guest OS resident <a class="zem_slink" href="https://en.wikipedia.org/wiki/ISCSI" rel="wikipedia" target="_blank" title="ISCSI">iSCSI</a> initiators</li>
</ol>
<h3>Namespace isolation</h3>
<p>When I say “namespace”, I mean not only a <a href="http://blog.scottlowe.org/2013/09/04/introducing-linux-network-namespaces/" target="_self">network namespace</a> although that certainly is a part of it.&#0160; I’m also referring to things like iSCSI IQNs and in fact anything that can be used to uniquely identify a resource that is remotely connectable.&#0160; One example where having more than one namespace would be useful is an environment that is using more than one “orchestration layer software” instance (e.g., two instances of OpenStack).&#0160; In this case, let’s assume we have two groups working with different OpenStack versions and they want to utilize the same Storage Array simultaneously and furthermore will connect to it via iSCSI.&#0160; Maybe one group is working with the Havana release performing QA testing in preparation for rolling out a service, while the other team is performing dev/integration testing with the Icehouse release.&#0160; For the sake of this example, let’s assume the array only supports a single namespace.</p>
<p><a class="asset-img-link" href="/brasstacks/virtual-storage-networks-part-2-requirements-for-multi-tenant-storage/6a013487ed263f970c01a73da5f3da970d.jpg" style="display: inline;"><img alt="One" border="0" class="asset  asset-image at-xid-6a013487ed263f970c01a73da5f3da970d image-full img-responsive" src="/brasstacks/virtual-storage-networks-part-2-requirements-for-multi-tenant-storage/6a013487ed263f970c01a73da5f3da970d.jpg" title="One" /></a></p>
<p>Although this may seem like a reasonable configuration, there are a number of problems:</p>
<ol>
<li>The Storage Array would need to be able to support multiple Cinder drivers simultaneously pulling from the same pool of physical resources.</li>
<li>The LUN Masking software on the array would need to be able to handle the case of a duplicate IQN being used without the risk of exposing one tenant’s data to another.&#0160; BTW, I’m not saying this is likely to happen, but it’s possible.</li>
<li>The duplicate IP Addresses used by both tenants would probably cause the biggest problem in this case (I mean, just look what&#39;s it&#39;s doing to &quot;Bumble&quot;).&#0160; Due to the way that routing and forwarding works, the array would be unable to determine which network interface to use when responding to an IO.</li>
</ol>
<p>As shown below, one possible solution to these problems would be to provide isolated namespaces for each OpenStack instance.</p>
<p><a class="asset-img-link" href="/brasstacks/virtual-storage-networks-part-2-requirements-for-multi-tenant-storage/6a013487ed263f970c01a3fceb3ed9970b.jpg" style="display: inline;"><img alt="Two" border="0" class="asset  asset-image at-xid-6a013487ed263f970c01a3fceb3ed9970b image-full img-responsive" src="/brasstacks/virtual-storage-networks-part-2-requirements-for-multi-tenant-storage/6a013487ed263f970c01a3fceb3ed9970b.jpg" title="Two" /></a></p>
<p>This could be achieved by utilizing a Virtual Storage Array (or something like it).&#0160; If you’re unfamiliar with this concept, you can think of each VSA as a Virtual Machine that provides storage services and contains its own network namespace.&#0160; As far as each VSA would be concerned it would be under the control of a single Cinder driver and would not see duplicate IP Addresses (as long as the Networks shown above are separate). &#0160;Also, since provisioning is done on a per VSA basis, there would be no issue with a duplicate (spoofed) IQN getting access to volumes that they shouldn’t.&#0160; Today, EMC supports the concept of a Virtual Data Mover (VDM) on the VNX platform but I would expect to see support for this feature expanded as it makes sense to do so.&#0160; For now let’s just assume that the concept of a VSA is useful in certain scenarios and that they can be dynamically instantiated as needed (like a VM).</p>
<h2>Prevent noisy neighbor problems</h2>
<p>When I use the term “noisy neighbor”, I’m referring to the ability of one network end device to negatively impact the effective Quality of Service (QoS) being experienced by another end device.&#0160; There are also many other types of noisy neighbor issues (e.g., spindle contention) that can be experienced by tenants that are sharing the same physical resource (e.g., physical disk).&#0160; Although these other types of noisy neighbor problems are serious ones that need to be addressed, they are not strictly related to connectivity, so I’m not going to attempt to discuss them here.&#0160; I will say that we have a group of very smart people working on physical resource sharing and they are continually enhancing our products to ensure the resources that are allocated are actually delivered to the end user.</p>
<p>In terms of a noisy neighbor as it applies to connectivity, using the previous diagram it’s probably not immediately apparent that there could be an issue.&#0160; However, if I redraw things slightly it should become a bit easier to understand.&#0160;</p>
<p><a class="asset-img-link" href="/brasstacks/virtual-storage-networks-part-2-requirements-for-multi-tenant-storage/6a013487ed263f970c01a73da5f459970d.jpg" style="display: inline;"><img alt="Three" border="0" class="asset  asset-image at-xid-6a013487ed263f970c01a73da5f459970d image-full img-responsive" src="/brasstacks/virtual-storage-networks-part-2-requirements-for-multi-tenant-storage/6a013487ed263f970c01a73da5f459970d.jpg" title="Three" /></a></p>
<p>The diagram shows both VSA instances are being connected to by a different physical host via a different Virtual Network instance.&#0160; This Virtual Network Instance could be a VLAN, a VXLAN or both VLAN and VXLAN.&#0160; I will be providing much more detail about this concept later in this series.&#0160; The point relevant to noisy neighbor prevention is that both VSAs share a common physical interface.&#0160; If this interface were using a lossless protocol such as FC, or a protocol that used DCB (FCoE and Lossless iSCSI), congestion in one VSA would impact traffic to the other VSA if all of the VSAs were using the same priority or more specifically CoS. &#0160;This is not only theoretically possible (since there are only 8 ethernet CoS), but in practice many switches only support a single lossless CoS, so it&#39;s likely that you’d encounter this situation.&#0160; If you’re interested in congestion spreading in a lossless network, check out the Congestion and backpressure section of the <a href="http://www.emc.com/collateral/hardware/technical-documentation/h4331-networked-storage-cncpts-prtcls-sol-gde.pdf" target="_self">Networked Storage Concepts and Protocols techbook</a>. &#0160;In the case when traditional iSCSI, File and even Object protocols are used, there’s nothing to prevent spikes in traffic in one Virtual Network from impacting the other.&#0160;&#0160; This problem can be exacerbated in a Virtual Server environment as shown below.</p>
<p><a class="asset-img-link" href="/brasstacks/virtual-storage-networks-part-2-requirements-for-multi-tenant-storage/6a013487ed263f970c01a5119ae94f970c.jpg" style="display: inline;"><img alt="Four" border="0" class="asset  asset-image at-xid-6a013487ed263f970c01a5119ae94f970c image-full img-responsive" src="/brasstacks/virtual-storage-networks-part-2-requirements-for-multi-tenant-storage/6a013487ed263f970c01a5119ae94f970c.jpg" title="Four" /></a></p>
<p>Although not explicitly shown in the diagram, the configuration above would require that the storage protocol in use be terminated in the VM.&#0160; While this is possible with iSCSI, it violates one of the requirements I’ll talk about later and in general is not done all that frequently anyway.&#0160; It’s much more likely that someone would want to use a File or Object based protocol in this kind of configuration.&#0160;&#0160; In any case, you can imagine that since both VMs are using the same physical connection and there’s no arbitration of network resource allocation being done, it’s possible for each end device to impact the effective QoS being observed by any of the others.</p>
<p>One theoretical solution to this problem would be to implement some kind of traffic shaping (TS) entity at the network edge as shown below.&#0160; The problem is, for reasons that are outside the scope of this post, guaranteeing end-to-end bandwidth for an arbitrary number of end points across an arbitrary network topology is something that has proven to be an elusive feature to develop.&#0160; &#0160;&#0160;</p>
<p><a class="asset-img-link" href="/brasstacks/virtual-storage-networks-part-2-requirements-for-multi-tenant-storage/6a013487ed263f970c01a3fceb3fe5970b.jpg" style="display: inline;"><img alt="Five" border="0" class="asset  asset-image at-xid-6a013487ed263f970c01a3fceb3fe5970b image-full img-responsive" src="/brasstacks/virtual-storage-networks-part-2-requirements-for-multi-tenant-storage/6a013487ed263f970c01a3fceb3fe5970b.jpg" title="Five" /></a></p>
<p>All of that in mind, let’s assume that it will be possible to use something like this approach to limit the amount of bandwidth consumed by an end device.&#0160; Although I do realize that this not the same thing as bandwidth guarantee, I’m only suggesting it because I know where I’m going with this line of reasoning.&#0160; I’ll just beg for your indulgence until I get to the topologies portion of this series.&#0160;</p>
<p>As I mentioned earlier, many end users don’t want to make use of iSCSI initiators that reside inside of the Guest (VM) and this further complicates things for us because of the way iSCSI traffic originates from a hypervisor such as ESX.&#0160; As shown below, the problem is unless you’re using an iSCSI HBA, there’s a single iSCSI Initiator instance and this has some interesting side effects.&#0160; The most important one from a connectivity point of view is that all iSCSI storage traffic appears to originate from a single iSCSI initiator.&#0160; Of course this single initiator can be presented out of multiple network interfaces but short of creating a data store for each VM and then making sure the LUNs in the datastore are only visible via a specific NIC, there’s currently no way to associate a particular VM and its associated IO with a particular network interface.&#0160; It seems like every time I point out this issue to someone, they start by asking “aren’t VVOLs are going to solve this problem?” and the answer is NO!&#0160; Again shown in the diagram below I’ve added some smaller disk shaped objects that are intended to represent VVOLs. &#0160;The point being VVOLs are a SCSI level entity that sit one level above iSCSI in the stack, so VVOLs allow for the identification of VMs but all IOs for a group of VVOLs that are being accessed at the same protocol endpoint will still experience the IO blender issue.&#0160;</p>
<p><a class="asset-img-link" href="/brasstacks/virtual-storage-networks-part-2-requirements-for-multi-tenant-storage/6a013487ed263f970c01a3fceb4066970b.jpg" style="display: inline;"><img alt="Six" border="0" class="asset  asset-image at-xid-6a013487ed263f970c01a3fceb4066970b image-full img-responsive" src="/brasstacks/virtual-storage-networks-part-2-requirements-for-multi-tenant-storage/6a013487ed263f970c01a3fceb4066970b.jpg" title="Six" /></a></p>
<p>An architecture that resolves the IO blender issue is shown below.&#0160; Note that there are multiple tenants each with their own iSCSI Initiator.&#0160; Traffic could be shaped on a per Initiator basis such that each tenant is allowed to consume a fixed amount of bandwidth.&#0160; Again, this is not a guarantee from the network, just a guarantee that on a per hypervisor basis each tenant can only consume a certain amount of network bandwidth.&#0160; VVols could still be used in this configuration to allow for per VM storage actions to be performed.&#0160;&#0160;</p>
<p><a class="asset-img-link" href="/brasstacks/virtual-storage-networks-part-2-requirements-for-multi-tenant-storage/6a013487ed263f970c01a5119ae9ed970c.jpg" style="display: inline;"><img alt="Seven" border="0" class="asset  asset-image at-xid-6a013487ed263f970c01a5119ae9ed970c image-full img-responsive" src="/brasstacks/virtual-storage-networks-part-2-requirements-for-multi-tenant-storage/6a013487ed263f970c01a5119ae9ed970c.jpg" title="Seven" /></a></p>
<p>So the astute reader will note that the vast majority of what is described above is not supported today and they would be right.&#0160; However, I will tell you that with the exception of VVols, we’ve set something like this up in the lab using LXC containers as the tenant entities and KVM VMs for the VMs.&#0160; We did run into a number of problems but that’s a story for another post.&#0160; BTW, as I was writing this I noticed a <a href="http://stu.radnidge.com/post/81366484323" target="_self">blog post</a> and thought the timing was funny given the fact that I’ve just essentially alluded to nested Hypervisors. :-)</p>
<p>All joking aside, the majority of the “tenant box” above could be implemented as management abstractions, the only piece required to eliminate the cross tenant IO blender effect is one initiator per tenant.&#0160; Keep in mind that each initiator would probably also want to exist in its own namespace for the reasons that I described in the “namespace isolation” section above.&#0160;</p>
<h2>Provide Bandwidth /IOPS / response time guarantees</h2>
<p>Above I described how a “traffic shaper” could enforce bandwidth utilization limits on a per tenant per server basis; I’ll come back to this later when I describe a couple of topologies that could meet all of the requirements.&#0160; In this section I will briefly discuss providing IOPS and Response Time (RT) guarantees.&#0160;</p>
<p>When my colleagues from the array teams talk about IOPS and RT, it’s typical for them to think of this in terms of the T4 (T = Time) segment of the diagram shown below.&#0160; This is because they know exactly when the target (labeled as T in the VSA) receives the IO, how long it takes them to complete it and how many times they do this on a per initiator per second basis.&#0160; Also when you provision storage and assign IOPS and RT performance parameters on the array, this is really the only way you can think about it.&#0160; This is because although the Array knows exactly how many IOPS it’s performed and whether or not it is capable of satisfying the IOPS allocated to each initiator, it has no way to determine (let along alter) how diagram segments T1, T2 and T3 are impacting the effective RT at the VM or how other factors (e.g., congestion in the network) are impacting the ability of a given initiator to perform the number of IOPS allocated to it.&#0160;</p>
<p><a class="asset-img-link" href="/brasstacks/virtual-storage-networks-part-2-requirements-for-multi-tenant-storage/6a013487ed263f970c01a5119aea9c970c.jpg" style="display: inline;"><img alt="Eight" border="0" class="asset  asset-image at-xid-6a013487ed263f970c01a5119aea9c970c image-full img-responsive" src="/brasstacks/virtual-storage-networks-part-2-requirements-for-multi-tenant-storage/6a013487ed263f970c01a5119aea9c970c.jpg" title="Eight" /></a></p>
<p>Some networking vendors, especially Brocade with their Fabric Vision concept, are trying to address this problem by adding functionality that allows them to monitor for and report congestion in segments T2,T3 and to a limited extent T4.&#0160; While this certainly represents a huge step in the right direction, I don’t believe it addresses segment T1.&#0160; In addition, although I know there are a number of customers using things like <a href="http://www.vmware.com/files/pdf/techpaper/VMW-vSphere41-SIOC.pdf" target="_self">Storage IO Control (SIOC)</a> with ESX, I don’t think it completely addresses this problem either.&#0160;</p>
<p>In my opinion, in order to address the problem from end-to-end (T1-T4), an additional block of functionality will need to be added and I’ve labeled it as “IOM” in the diagram above.&#0160; As I&#39;ll describe in subsequent sections, the IOM (I/O Manager) would ideally contain three functions:</p>
<ol>
<li>IOPS and Response Time (RT) Monitoring</li>
<li>Remediation for IOPS and Response Time related issues</li>
<li>Encryption</li>
</ol>
<p>For now, we&#39;ll just focus on the first two and discuss encryption later.</p>
<p>Monitoring for Response Time was breifly described above and is fairly straight forward. &#0160;Essentially the IOM would put a timestamp on each I/O as it &quot;enters&quot; the module. &#0160;When the I/O completes the total IO completion time can be calculated. &#0160;</p>
<ul>
<li>If the I/O completed within the allocated time no additional action would be required but the completion time value could be stored for some period of time. &#0160;Perhaps even a rolled up average could be stored for longer periods of time. &#0160;</li>
<li>If the I/O did not complete within the allocated time, this condition could be flagged. &#0160;If enough of these conditions occurred in a pre-defined period of time, the remediation functionality could be invoked. &#0160;I&#39;ll provide more detail on this below. &#0160; &#0160;</li>
</ul>
<p>Monitoring for IOPS is a bit more convoluted because although you could set a minimum IOPS threshold, you would need to be able to distinguish between the following two cases:</p>
<ol>
<li>a VM would like to perform additional I/O but it cannot for some resource related reason, or</li>
<li>it just doesn&#39;t have any more I/O to perform that second.</li>
</ol>
<p>The solution to the above would almost certainly involve monitoring I/O queues and would be implementation specific.&#0160;</p>
<p>Once you&#39;ve identified an IOPS or Response Time related issue, the remediation functionality would need to determine the correct action to take to resolve the issue. &#0160;The action could be taken automatically and this would be the expected action for severe issues. &#0160;One example would be a path going down (loss of a link) and the action that something like PowerPath would take to resolve it. &#0160;The action could also be simply to notify the administrator and this might be a better remediation step for chronic issues, especially if the remediation step involves relocating the storage volume to another array (e.g., <a href="/brasstacks/fast-sideways-a-connectivity-point-of-view/" target="_self">FAST Sideways</a>). &#0160;&#0160; &#0160;&#0160;</p>
<h2>Tenant traffic identification</h2>
<p>The basic idea behind this one is to allow for the identification of frames or packets that belong to a given tenant and to be able to perform this identification anywhere in the infrastructure. &#0160;At least one Customer was interested in the feature for a security related reason.</p>
<p>For better or worse, when I think of a tenant, I tend to think in terms of vCloud Director and its concept of an Organization VDC, see below for my graphical interpretation.</p>
<p>&#0160; &#0160;<a class="asset-img-link" href="/brasstacks/virtual-storage-networks-part-2-requirements-for-multi-tenant-storage/6a013487ed263f970c01a73dac5997970d.jpg" style="display: inline;"><img alt="Vcd" border="0" class="asset  asset-image at-xid-6a013487ed263f970c01a73dac5997970d image-full img-responsive" src="/brasstacks/virtual-storage-networks-part-2-requirements-for-multi-tenant-storage/6a013487ed263f970c01a73dac5997970d.jpg" title="Vcd" /></a></p>
<p>If we use this model and we decide that we want the ability to identify a tenant&#39;s traffic between the Initiator (labeled INIT) and the storage (the blue or red &quot;soup can&quot; shape above the INIT), then we would need to isolate each tenant onto a separate physical host. &#0160;Again, as I described above, the reason for this has to do with the relationship of an iSCSI initiator to a ESX host. &#0160;This relationship also has implications to Storage Network Service Insertion as I describe below. &#0160;&#0160;</p>
<h2>Storage Network Service Insertion</h2>
<p>Storage Network Service Insertion is similar to <a href="http://packetpushers.net/virtualizing-network-services-part-1-the-beginning/" target="_self">Network Service Insertion</a>.&#0160; Both Network Service Insertion and Storage Network Service Insertion support:</p>
<ul>
<li>dynamic service insertion (e.g., inserting a new service into an existing flow); and</li>
<li>service composition (e.g., building a network service and then deploying it for use).&#0160;</li>
</ul>
<p>Examples of dynamic Storage Network Service Insertion could be:</p>
<ul>
<li>the addition of an inflight encryption appliance;</li>
<li>the redirection of a flow to a security appliance for a closer look at access patterns, etc; or</li>
<li>the <a href="/brasstacks/fast-sideways-a-connectivity-point-of-view/" target="_self">FAST Sideways</a> use case. &#0160;Essentially, you could migrate a storage volume to a different storage appliance and take advantage of features supported by that appliance.&#0160;</li>
</ul>
<p>The above use cases require that tenant flows be isolatable and this is one of the reasons that we think one initiator per tenant is interesting.</p>
<p>An example of Storage Service composition, is shown below.</p>
<p><a class="asset-img-link" href="/brasstacks/virtual-storage-networks-part-2-requirements-for-multi-tenant-storage/6a013487ed263f970c01a3fceb4284970b.jpg" style="display: inline;"><img alt="Ten" border="0" class="asset  asset-image at-xid-6a013487ed263f970c01a3fceb4284970b image-full img-responsive" src="/brasstacks/virtual-storage-networks-part-2-requirements-for-multi-tenant-storage/6a013487ed263f970c01a3fceb4284970b.jpg" title="Ten" /></a></p>
<p>Typically, I like to think about Service Composition in terms of a user requesting a specific amount of capacity with a set of desired attributes.&#0160; I won’t go into details about the services themselves and how they relate to one another other than to say that in this case:&#0160;&#0160;</p>
<ul>
<li>the Initiator on the Hypervisor would access a Virtual Volume on the VPLEX</li>
<li>The Virtual Volume would in reality consist of multiple services each being provided as follows:</li>
<ul>
<li>VPLEX would provide the &quot;distributed cache coherency&quot; and &quot;addressability&quot; services</li>
<li>VMAX would provide the &quot;storage capacity&quot; service</li>
<li>Data Domain would provide the &quot;dedup&quot; service</li>
</ul>
</ul>
<p>The important piece to consider here is that these Storage Service Compositions could be dynamically created as needed without the need for pre-provisioning or manually configuring connectivity.</p>
<h2>Authentication (and Encryption)</h2>
<p>The customers we spoke with not only wanted the ability to authenticate the identity of an Initiator and a Target. &#0160;As we dug into this requirement some more it turned out at least one of them also wanted the ability to provide Encryption as a Service (EaaS) to their tenants.&#0160; Originally when we were talking about EaaS, we were thinking about it in terms of a service that you could insert between the initiator and a trusted network device. &#0160;Once encrypted, the flow could take any path to reach another trusted portion of a network then be decrypted and sent to its Storage Target.&#0160; This seemed to work for many use cases. &#0160;However, eyes really seemed to light up when we asked if it would make sense to put this functionality inside of the IOM block I described above.</p>
<p>The basic idea is that the tenant would purchase the encryption service from the service provider and part of the provisioning process would involve the IOM interacting with a key manager on behalf of the tenant perhaps using <a href="https://www.oasis-open.org/committees/tc_home.php?wg_abbrev=kmip" target="_self">KMIP</a>. &#0160;The idea is to provide tenant level encryption without requiring tenant involvement in the key management process.</p>
<h2>Do not require Guest resident iSCSI Initiators</h2>
<p>At least one of the customers we spoke with had supportability and security concerns with an approach that relied on iSCSI initiators being installed in the Guest OS (VM).&#0160;</p>
<p>As it turns out, we had a scalability concern with this approach especially if every VM (up to 4000 in a rack) were to utilize a common storage array. &#0160;The problem is each login consumes system resources and potentially creates management complexity. &#0160;Because of this problem and due to the fact that at least one customer didn&#39;t like the approach, we decided to focused on per tenant iSCSI Initiators (when iSCSI is required)</p>
