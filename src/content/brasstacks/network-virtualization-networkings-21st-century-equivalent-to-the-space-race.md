<p>This post was written with Patrick Mullaney.</p>
<p><strong>Overview&#0160;&#0160;&#0160; </strong></p>
<p>Similar to the milestones in the <a href="http://www.thespacerace.com/timeline/" target="_self">space race timeline</a>, I believe that Monday July 23<sup>rd</sup> (the day VMware announced plans to acquire Nicira) will be viewed by networking enthusiasts as a significant milestone in the evolution of our discipline.&#0160; Just to keep this in perspective, two other significant milestones will probably be Cisco’s Insieme announcement, but not for the reason you might think and Oracle’s announcement of plans to acquire Xsigo.&#0160; </p>
<p>Of course chronologically the announcements were Insieme, Nicira and Xsigo.&#0160; And since Insieme&#0160;seems to&#0160;be more about <a href="http://www.networkworld.com/community/blog/meet-ciscoinsiemes-recruiter" target="_self">Cisco entering the storage market</a> than about anything else, I’d like to think that a causal link exists between the three announcements in the same order.&#0160; However, I have absolutely no proof of this and while further speculation might be a great topic for a&#0160;techno-drama, it would ultimately be irresponsible.&#0160; As a result, I’ll spend the rest of this post providing a high level overview of Network Virtualization, how it relates to Software Defined Networking and this may allow you to speculate on what the next major milestones in the NV race may be...</p>
<p><strong>Getting down to Brass-Tacks</strong></p>
<p>Network Virtualization (NV) and its big brother Software Defined Networking (SDN) both attempt to address a set of <a href="http://www.sdncentral.com/sdn-use-cases/" target="_self">use cases</a> that have proven difficult to handle while using traditional Networking gear.&#0160; These challenges range from the more esoteric (e.g., the Virtual Patch Panel) to the more well known (e.g., automating L2 extension to support ease of VM migration).&#0160; As described by <a href="http://etherealmind.com/openflow-software-defined-networking-routing-or-switching/" target="_self">Greg Ferro</a> the basic idea is to separate the traditionally monolithic switch platform into three separate constructs known as the Data Plane, the Control Plane and the Management Plane.&#0160; As shown below, once this is done, the Management and Control plane elements can span multiple Data Plane elements thereby allowing them to be programmed based on the Management and Control planes greater understanding of the end to end connectivity requirements. </p>
<p><a class="asset-img-link" href="/brasstacks/network-virtualization-networkings-21st-century-equivalent-to-the-space-race/6a013487ed263f970c01761776a55b970c.jpg" style="display: inline;"><img alt="One" border="0" class="asset  asset-image at-xid-6a013487ed263f970c01761776a55b970c image-full" src="/brasstacks/network-virtualization-networkings-21st-century-equivalent-to-the-space-race/6a013487ed263f970c01761776a55b970c.jpg" title="One" /></a></p>
<p>BTW, as described in David Black’s <a href="http://www.ietf.org/proceedings/83/slides/slides-83-nvo3-1.pptx" target="_self">nvo3 BoF presentation</a> these relationships present some very interesting challenges to the management applications that will operate in this space.&#0160; </p>
<p><strong>Network Virtualization and Software Defined Networking</strong></p>
<p>If the diagram above was a little bit too abstract for you, the diagram below should make the relationship between Network Virtualization (NV) and Software Defined Networking (SDN) a bit easier to understand.&#0160; Please understand, because I am trying to make the topic as approachable as possible, I’m using a very simple topology.&#0160; As a result, some of the options, such as a device that participates in both the underlay and overlay (e.g., a NV gateway) is not being shown.&#0160; I’ll save that for a later post.&#0160; &#0160;</p>
<p><a class="asset-img-link" href="/brasstacks/network-virtualization-networkings-21st-century-equivalent-to-the-space-race/6a013487ed263f970c0177445d2ef5970d.jpg" style="display: inline;"><img alt="Two" border="0" class="asset  asset-image at-xid-6a013487ed263f970c0177445d2ef5970d image-full" src="/brasstacks/network-virtualization-networkings-21st-century-equivalent-to-the-space-race/6a013487ed263f970c0177445d2ef5970d.jpg" title="Two" /></a></p>
<p><strong>The Underlay Network</strong></p>
<p>Before you can use a Network Virtualization Overlay(NVO), you need to have network connectivity between the NV edges.&#0160; This connectivity is provided by the underlay network and today can be provided by anything from a L2 LAN segment (e.g., a single L2 switch, or Ethernet Fabric such as Brocade VCS or Juniper’s QFabric) to a L3 ECMP based network.&#0160; Whatever you choose, the underlay must be capable of providing an adequate amount of bandwidth to support the bandwidth requirements of the overlay.&#0160; These bandwidth requirements can be met by either statically configuring the underlay to provide the appropriate bandwidth or could be dynamically met by using an SDN approach to steer flows over links that provide an adequate amount of bandwidth.&#0160; This steering function could be provided by the Management and Control Planes by using OpenFlow to configure the Data Plane.&#0160;&#0160;&#0160;</p>
<p>I should point out that all of the work I have done with NV (so far) has used the &quot;statically configured&quot; underlay&#0160;approach and this has worked fine for the very simple Proof of Concept (PoC) work that I have been participating in.&#0160; This is a roundabout way of saying that I haven’t done much work with the “traditional?” SDN space nor tried to scale up the PoC configuration and as a result, I don’t have a good fact-based opinion on how much of a need there will actually be for these SDN based steering functions. </p>
<p>That having been said, my advice to anyone trying to setup a NV based PoC would be to:</p>
<ol>
<li>setup a statically configured underlay.&#0160; I’m using an L2 topology.</li>
<li>Verify end to end connectivity between all of the NV Edges, ping works fine..</li>
<li>Once items 1 and 2 have been completed, mentally wrap the underlay network in a box, stick the box under your desk and forget about it!</li>
<li>Once the <a class="zem_slink" href="https://en.wikipedia.org/wiki/Overlay_network" rel="wikipedia" target="_blank" title="Overlay network">overlay network</a> is up and you are sending and receiving packets via the overlay, then you can worry about optimizing the underlay.&#0160;</li>
</ol>
<p>My point is you can and probably should (at least initially) treat the underlay and overlay as different entities and avoid being overwhelmed by the complexity of trying to configure both at the same time.</p>
<p><strong>The Overlay Network</strong></p>
<p>The Overlay Network I have been using is STT based.&#0160; The Management and Control Plane functionality is being provided by Nicira’s Network Virtualization Platform (NVP) and the Data Plane is Open vSwitch based.</p>
<p>Before I go any further, it’s important to note that gained access to the NVP software for free as a part of a PoC that I’m merely participating in. </p>
<p>When I was first introduced to NVP, I had a hard time understanding some of the basic NV concepts and terminology, so I am going to focus on those aspects for now.&#0160; To start with, based on some work that I’ve done with VMware’s vCloud Director recently, I think if you understand vCDNI or even just the concept of a distributed vSwitch, you’ll have a pretty easy time understanding the type of functionality that NVP enables.</p>
<p>At a high level, NVP allows you to create distributed vSwitches (referred to as Transport Zones in NVP) that you can then attach tenants to.&#0160; A tenant is simply a group of network devices that only have visibility to other network devices that also belong to that tenant.&#0160; In NVP, tenants are attached to Virtual Interfaces on one or more Logical Switches.&#0160; Each Logical Switch is associated with a Transport Zone. The easiest way to visualize a tenant is to think of each one as a different company that is utilizing the same physical infrastructure as another company.&#0160; To make these relationships a bit less abstract, refer to the following diagram that is a slightly modified version of the one I provided above.&#0160; </p>
<p><a class="asset-img-link" href="/brasstacks/network-virtualization-networkings-21st-century-equivalent-to-the-space-race/6a013487ed263f970c017c317f9fce970b.jpg" style="display: inline;"><img alt="Three" border="0" class="asset  asset-image at-xid-6a013487ed263f970c017c317f9fce970b image-full" src="/brasstacks/network-virtualization-networkings-21st-century-equivalent-to-the-space-race/6a013487ed263f970c017c317f9fce970b.jpg" title="Three" /></a><br />&#0160;</p>
<p>Note that both the VMs and the ports they connect to on the OVS instance have been color coded.&#0160; Each color is intended to represent a different tenant or company.&#0160; Obviously these different companies will want isolation from one another and the tenant concept allows for this and allows for them to also be managed separately.&#0160; From a protocol perspective, this isolation is enforced by including a tenant ID in the header of each frame passed between the NV edges.&#0160; Regardless of the tenant ID, these frames can use some or all of the links between the two OVS instances shown.&#0160;&#0160; </p>
<p>The tenant ID can be something as simple as a VLAN tag, MPLS label or be part of an encapsulation format that has been specifically designed to support NV such as <a href="http://tools.ietf.org/html/draft-sridharan-virtualization-nvgre-01" target="_self">NVGRE</a>, <a href="http://tools.ietf.org/html/draft-mahalingam-dutt-dcops-vxlan-02" target="_self">VXLAN</a>&#0160;or <a href="http://tools.ietf.org/html/draft-davie-stt-01" target="_self">STT</a>.&#0160; Each of these approaches has their pros and cons and are being actively debated in the IETF working group called <a href="http://datatracker.ietf.org/wg/nvo3/charter/" target="_self">nvo3</a>.&#0160; As I mentioned previously, we’re using STT and the performance results have been impressive.&#0160; For a interesting performance comparison of the different encapsulation methods, see <a href="http://networkheresy.com/2012/06/08/the-overhead-of-software-tunneling/" target="_self">this post</a>&#0160;by Martin Cassado.&#0160; During the PoC we also performed some basic performance testing with STT and it supports the data that Martin provides in his post.&#0160; </p>

<p><span style="text-decoration: underline;">Physical Topology</span></p>
<p>The physical topology consisted of a couple of hosts that each had a single dual port 10GbE NIC.&#0160; Each NIC was connected to a different 10G Ethernet switch.</p>
<p>The Ethernet switches were configured to be a part of the same MLAG and this allowed us to setup and use bonding on the hosts.</p>
<p>We then created a total of 9 “VMs” on each Physical host and loaded NetPerf onto both the Initiator and Target VMs.&#0160; I am intentionally being vague about the VM type we used but I’ll tell you it wasn’t VMware based.</p>

<p>The Y-axis is in Gbps and represents the throughput observed coming out of the adapter.&#0160; These numbers were generated by NetPerf but were verified by using an XGIG analyzer.&#0160; The X-axis represents the number of pairs of VMs that were running traffic during the test.&#0160; </p>
<p>Note that a single pair of VMs was able to generate about 8Gbps and that as we scaled this up, the amount of bandwidth consumed approached the maximum available bandwidth of 20Gbps.</p>
<p>Also note that test 3 had an interesting result.&#0160; I believe this was the result of multiple flows being stacked on the same physical link while the other link remained under utilized.&#0160; Perhaps this is one of those areas where SDN could help.</p>
<p>Also note that while running with 9 pairs on test run 1, we apparently achieve greater than 20Gbps and this was the result of my manual (staggered start) testing process and the short duration of the tests.</p>
